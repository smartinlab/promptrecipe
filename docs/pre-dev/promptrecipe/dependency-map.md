## Decision 1 — Composition Engine: **BUILD**

Unchanged from revision 1, and the reasoning is language-independent.

**Selected:** a purpose-built bounded directive language — hand-written lexer and recursive-descent parser, total expression evaluator. **No template engine, no parser generator.**

| Constraint (TRD §9.5) | Built | Adopted general-purpose engine |
|---|---|---|
| **E1** fragment never rendered as a template | **by construction** — no "render this content" production exists | only by refusing its include mechanism — a discipline, policed forever |
| **E2** inserted value never re-parsed | **by construction** | depends on engine render semantics; re-verify each upgrade |
| **E3** total evaluation | **by construction** — no call/loop/IO production | requires disabling much of the engine |
| **E4** structure resolved before substitution | **by construction** — pass ordering is ours | fights a single-pass render model |
| **E5** no ordering from map/set/filesystem/locale | ours to guarantee | depends on internals we do not control |
| **E6** resolver hook owned by our Resolution component | trivially — no built-in file lookup to override | available in mature engines (their genuine advantage) |
| **E7** position-and-cause errors | ours to design | inherited, usually good |

**6 of 7 satisfied by construction; an adopted engine satisfies at most 2.**

**Rejected:** mature general-purpose engines (Gate 0 documented four sandbox-escape CVEs on one such engine's sandbox, each fix followed by a new indirect route — and our fragments may be optimizer-written, which is adversarial input by definition) · logic-less engines (lack the conditional expressiveness, and most still render included content) · parser generators (a hand-written parser gives better error positions for a grammar this small, and adds no dependency).

**The grammar in full:** literals · comparisons · boolean operators · membership · variable references · load directive · order declaration · expectations. Deliberately smaller than any general-purpose engine — which is why building it is proportionate.

## Decision 2 — Host Language: **Python only** *(reversed in revision 2)*

**Selected:** pure Python. No compiled core, no bindings, no FFI.

### Why the original performance concern does not hold

The concern was that Python would be too slow for the template core. Examining what that core actually does, per call, for a typical ~50-fragment recipe:

| Step | Estimated cost in pure Python |
|---|---|
| Parse the recipe (~2 KB) | **1–3 ms** — the only slow step, and it is cacheable |
| Evaluate ~30 conditions over a small tree | ~50–100 µs |
| Resolve 50 paths (dict lookups, string ops) | ~100 µs |
| Fetch fragments (warm cache) | ~50 µs |
| Join 50 fragments / ~50 KB | ~20 µs — `str.join` is C |
| Value substitution, single pass | ~100–200 µs |
| Two digests over ~50 KB | ~100 µs — the hashing library is Rust-backed |

**Warm: well under 1 ms. Cold: 1–4 ms.** TRD §8 targets <10 ms warm and <200 ms cold. Both met with room.

**The parse — the only slow step — is cacheable by content identity**, a primitive the design already has (ADR-002). Parse once per recipe *version*, not per call, and the cost disappears after the first assembly.

**And the decisive context:** this sits on the request path of a model call, which takes 500 ms–30 s. Even a 4 ms assembly is **0.01%–0.8%** of end-to-end latency. Optimizing it is invisible.

> ⚠️ **These are reasoned estimates from known operation costs, not measurements.** No benchmark could be run in this session. **Task T-005 now carries a subtask that measures the assembly path against the §8 budget for real** — so this decision stops resting on my estimate.

### The crux: the one genuinely hot operation is already compiled

Content identity is computed on every fragment read, and it is the only step where raw throughput matters. The chosen hashing library **ships as a Rust implementation behind a Python wheel**. We get compiled-language speed exactly where it matters **without owning a Rust project**.

### What Python-only buys, concretely

| Benefit | Why it matters here |
|---|---|
| **Native optimization integration** | The optimization target is Python-only. A compiled core would put an FFI boundary on the fragment write-back path (FR-026) — the integration the product's differentiator depends on |
| **Native agent-framework integration** | The frameworks the stakeholder named are Python. FR-038 becomes trivial rather than a binding exercise |
| **One toolchain** | A compiled core meant three (compiler, Python packaging, multi-platform CI matrix) |
| **Contributors can contribute** | The audience is people who write prompts. Requiring a systems language to touch the core is a steep barrier |
| **Fast iteration while the design still moves** | This design took eight stakeholder amendments to reach its current shape. That is healthy, and it argues for a fast edit-run loop |

### The sequencing argument

The four never-regress properties (P1 determinism, P2 order-aware identity, P3 no evaluation of fragment content, P4 no partial output) hold identically in Python — `hypothesis` does what a property-testing library in any language does.

**Those properties make a future port verifiable.** If profiling ever shows assembly matters, port the core and the same properties prove the port is behaviour-identical. **Starting in Python does not close the compiled-core door; starting compiled would close the fast-iteration door now.**

### What would change this decision

Assembling **thousands of prompts per second** in a batch loop, or libraries of **100k+ fragments**. TRD §8 explicitly scopes to "thousands, not millions", and even a large evaluation sweep is dominated by model calls and by the evaluation tool's own subprocess overhead.

## Decision 3 — Content Identity (ADR-002)

| Selection | Version | Verified |
|---|---|---|
| **BLAKE3**, package `blake3` | **1.0.9** (`requires_python >=3.8`) | [PyPI](https://pypi.org/pypi/blake3/json), 2026-08-31 |

**Encoding:** full 256-bit digest, lowercase hex; displayed truncated to 12 characters **always alongside the path**, stored in full.

**Justification:** identity is computed on every fragment read, so digest speed is on the hot path (TRD §8). BLAKE3 is substantially faster than SHA-2 while remaining a 256-bit cryptographic hash — and identity is a **trust boundary** (TRD §6.2: identity verification detects fragment substitution by a hostile custody backend), so a non-cryptographic hash cannot serve the role. This package ships a compiled implementation, which is where Decision 2's "hot operation is already compiled" claim comes from.

| Alternative | Why rejected |
|---|---|
| **`hashlib.sha256`** (stdlib, zero dependencies) | Genuinely tempting — it would make the library dependency-free. Rejected on hot-path speed. **Reconsider if interoperability with an external content-addressed system becomes a requirement**, or if reducing to zero runtime dependencies proves more valuable than the speed |
| Non-cryptographic hash (xxHash family) | Faster, but cannot serve the tamper-detection role |

**Risk:** BLAKE3 is less universally implemented than SHA-256. Mitigation: the digest function is isolated behind one identity module, and **the algorithm name is recorded in the attestation**, so a future migration is detectable rather than silent.

## Decision 4 — Provenance & Attestation Format

**Selected:** a purpose-built record, serialized with the **standard library's `json`**. No serialization dependency.

**Two representations per TRD C4:** a lightweight span map (which fragment produced which portion — produced inline) and an assembly attestation (`subject` · `resolved_dependencies[]` · `condition_outcomes` · `resolved_order` · `address_resolutions` · `value_bindings` · `producer` · `structural_identity` · `instance_identity`).

**Shaped after supply-chain attestation** (subject + resolved dependencies + producer) because that model already solves "bind an output to its exact inputs" — but **not adopting the full specification**, whose signing and envelope machinery serves cross-organizational trust that no requirement here calls for. The shape matches, so adopting it later is a migration rather than a rewrite.

**Two-level identity (ADR-005)** computed here: `structural_identity` excludes value bindings; `instance_identity` includes them. Both are BLAKE3 over **canonically ordered** fields — canonical ordering is mandatory, since a serialization-order-dependent digest would break determinism (TRD §4). Timestamps appear as metadata and are **excluded from both digests**.

> Deliberately not adopted: a fast third-party JSON library. The attestation is small and written once per assembly; stdlib `json` is not the bottleneck, and a dependency-free serialization path is worth more than microseconds here.

## Decision 5 — Custody Backend Adapters

TRD C1 port: `exists` · `read` · `list` · `versions`. **No third-party package** — the standard library covers it.

| Backend | Phase | Implementation | Notes |
|---|---|---|---|
| **Local filesystem** | **1** | `pathlib` (stdlib) | One fragment = one file, satisfying ADR-007's hard constraint that a fragment be separately diffable |
| **Version-controlled** | **2** | Read the working tree via `pathlib`; shell out via `subprocess` for history | Deliberate: amendment 7 **delegates** review/history/origin to version control, and delegation means not reimplementing it. | **Remote object store** | **4** | **Deferred — no package selected at this gate** | Selecting now would fix a vendor before the requirement is validated; versions will have moved by Phase 4 |

> ### ⚠️ Unresolved gap carried forward from the TRD

This gate does not choose either; doing so would settle a product question inside a technology document. **Must be decided before Phase 4 ships.**

## Decision 6 — Integration Adapters *(now native — no FFI)*

Both targets changed ownership within eight months (Gate 0), so adapters stay **thin and optional**; the core must survive either disappearing. Python-only removes the process boundary revision 1 would have imposed on the optimization side.

| Target | Version | Adapter shape |
|---|---|---|
| **Evaluation tooling** | **0.122.2** (Node ≥22.22.0) | A Python callable prompt-source receiving `{vars, provider}` and returning a string or message array — the documented polyglot seam. Plus a **pass-through provider** returning the prompt instead of calling a model, which makes fragment-level text assertions cost zero model execution (FR-025). Assertions read `context.prompt` |
| **Optimization tooling** | **3.3.1** (Python `>=3.10,<3.15`) | **Now in-process.** Export one fragment's text to seed an instruction slot; import returned text as a proposal against that fragment path. **Per-fragment only** — SD11: no sub-prompt attribution exists |
| **Agent frameworks** | **Not pinned — deliberately** | FR-038 requires **zero fragment awareness** on the consumer's side; `get_prompt` returns a plain `str`. Depending on a specific framework would violate the requirement it serves |

**No integration target is a runtime dependency.** All adapters are optional extras.

| Purpose | Selection | Version | Verified | Justification |
|---|---|---|---|---|
| **Test runner** | `pytest` | **9.1.1** (`>=3.10`) | [PyPI](https://pypi.org/pypi/pytest/json), 2026-08-31 | Standard |

Determinism and order-aware identity are **property** claims — example tests cannot establish them |
| **Lint + format** | `ruff` | **0.16.5** | [PyPI](https://pypi.org/pypi/ruff/json), 2026-08-31 | One tool for both; fast enough to run on every save |
| **Build backend** | `hatchling` | **1.32.0** (`>=3.10`) | [PyPI](https://pypi.org/pypi/hatchling/json), 2026-08-31 | Standards-based (PEP 517/621), no plugin sprawl |
| **Type checking** | *(deferred)* | — | — | Not selected at this gate. Revisit once the public surface stabilizes; a wrong choice now is churn |

### The four property tests required from Phase 1

1. **Determinism** — repeated assembly of identical inputs yields byte-identical output and identical identities, **across processes**.
2. **Order-aware structural identity** — permuting fragment order changes the structural identity. *(Guards a silent failure: an order-blind identity corrupts every comparison without erroring.)*
3. **Identity separation** — differing value bindings preserve structural identity but change instance identity.
4. **No partial output** — every failure path emits nothing.

Plus **FR-028 in CI**: a timed scripted walkthrough failing the build if first value exceeds 30 minutes.
Plus **new in revision 2**: a **benchmark asserting the TRD §8 budget**, so Decision 2 rests on measurement rather than on this document's estimates.
